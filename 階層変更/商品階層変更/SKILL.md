# 商品阶层变更

## 目标与边界

将旧商品阶层上的自动订货及关联系统参数，按经批准的新旧阶层关系继承到新商品阶层。

仅处理：

`部門 → ミニ部門 → 品種 → 品目 → サブセグ`

若请求包含支社、支店、エリア或店舗所属变更，先拆分任务；本 Skill 不生成店铺阶层的继承关系或执行步骤。

## 开始前采访

执行前确认以下项目。缺少会影响结果的项目时必须询问，不得擅自假设：

1. 商品阶层变更日及作业时区。
2. 新阶层确定版、旧阶层基准版、文件版号与接收时间。
3. ProductsSet 期号/表名及数据库环境。
4. 影响范围：新规部門、部門－ゾーン、新规ゾーン、惣菜、寿司、野菜果物、需要预测、KPI除外、DIV。
5. 本次需要的产物：继承关系、复查SQL、Excel手顺、执行支援、验证报告中的哪些项。
6. 是否获准操作生产环境；未明确授权时只生成命令和检查表，不执行写入。

## 固定规则

- 新旧阶层关系是本体；付带SQL、JOB、报表不得替代继承关系确认。
- 每个命令、SQL、WEB点击和检查各占一行，逐行勾选；一行不得放多个可独立执行的动作。
- 写入前必须完成：备份、事前SELECT/件数、双人复核、回退方法。
- 名称推断不得直接投入生产；必须用ProductCD/JAN分布复查并取得业务批准。
- 固定年月、固定CD及上期SQL不得原样复用。
- 不在输出、日志或Skill中保存密码、令牌等认证信息。
- 异常时停止后续步骤，记录时间、对象、命令、件数、错误和已完成范围。

## 工作流

### 1. 固定基准与计算日期

以商品阶层变更日 `D` 为唯一基准，计算：

- 参数登记期限：`D-7`
- TBL除外设定参考日：`D-3`
- Master转送设定期限：`D-2`
- 旧阶层最终日：`D-1`
- 新阶层确认日：`D+1`
- KPI指定日：通常`D+1`；若`D+1`为周一则使用`D+2`
- 帐票洗替开始日：通常当周周一；若D为周一则取前一周周一
- 帐票洗替结束日：`D`

在所有命令和SQL中引用这些变量，不手工散写日期。

### 2. 整理并确认继承关系

读取并遵循个人 Skill `department_migration_workflow`：

1. 逐层独立比较CD路径和名称路径。
2. 对新规节点推定旧阶层继承源。
3. 从下层多数关系反向复核上层。
4. 读取并遵循 `department_migration_sql`，用旧Products与新ProductsSet按ProductCD关联复查。
5. 主来源占比低于70%时标记“要目検確認”，不得强制归为单一来源。
6. 所有修正记录修正前、修正后、理由及确认人。
7. 取得业务批准后，输出WEB登记用“新阶层:旧阶层=1:1”数据。

未批准行不得进入登记阶段。

### 3. 生成实施手顺

按以下阶段生成一份可执行清单：

1. 共通开始与资料冻结
2. 商品阶层整理与批准
3. 商品阶层1:1登记及最终确认
4. 部門相关参数准备
5. 切换前验证
6. 当日Master取得与参数备份
7. 商品阶层变更作业
8. KPI、条件JOB与帐票洗替
9. 切换后验证
10. 实绩记录与完了联络

详细门禁与条件见 [reference.md](reference.md)。

### 4. WEB操作

WEB步骤必须写出：

- 画面/菜单路径
- 输入值或文件
- 单次点击动作
- 期待结果
- 异常时处理

商品阶层登记的顺序固定为：

1. 下载当期商品阶层格式。
2. 登记批准后的1:1对应数据。
3. 状态设为“確定”，变更日设为D。
4. 执行商品阶层“最終確認”，确认未确定件数为0。
5. 当日先执行商品参数备份。
6. 选择同一变更日后执行商品阶层“変更作業”。
7. 确认所有对象表的开始和结束状态。

### 5. JOB星期判定

只在商品阶层变更对象成立且业务对象为“有”时判定：

- 惣菜：仅星期一再执行。
- 寿司：仅星期二再执行。
- 野菜・果物：仅星期三再执行。
- 其他星期只完成参数准备，不再执行对应JOB。

不得因“准备数据已完成”而忽略星期限制。

### 6. 切换前后验证

切换前确认新阶层尚未提前出现；切换后确认：

- masterdb：departments、subdepartments、varieties、items、subsegments。
- productsdb：新部門下存在商品。
- SMART TBL：部門至品目/サブセグ名称阶层存在且件数合理。
- 部門－ゾーン：需要变更时组合唯一且正确。
- 自动订货WEB：旧阶层参数已继承到新阶层。
- 惣菜等关联参数：与批准文件一致。
- 登记源件数、处理件数、完成件数一致。

列名、连接目标和TBL布局必须在执行前按当前环境确认，不照抄历史值。

## 输出格式

默认按 [output-template.md](output-template.md) 输出。至少包含：

- 输入资料和版本
- 条件判定
- 日期计划
- 新旧继承关系与批准状态
- 一行一检查的实施步骤
- 切换前后验证
- JOB执行/跳过及理由
- 件数差异、异常、回退和残课题

## 完成条件

只有同时满足以下条件才能报告完成：

- 继承关系已用商品数据复查并批准。
- 所有必需行均已完成，条件外行有明确跳过理由。
- WEB登记件数、处理件数、验证件数一致。
- 条件JOB符合星期规则。
- 切换后DB、TBL、WEB参数一致。
- 备份、执行记录、异常和完了联络均已留存。
