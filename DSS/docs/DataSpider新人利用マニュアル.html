西友データ連携での DSS の位置

DSS はシステム間 EAI/ETL であり、分析基盤ではない。選定はガイドライン P.18。高 Tier は DataHub。分析蓄積は Databricks。DSS は中低 Tier のファイル / DB 連携向き。

方式主な用途
DataHub高 Tier、冗長が要るファイル連携
DataSpiderシステム間のファイル / DB
Databricks蓄積、分析。書き込みは ADLS（MS0007）
Lakehouse Federation外部の最新状態を参照するだけ。参照元負荷に配慮

ADLS：IF ごとに 1 コンテナ。外部は SFTP。約 30 日で自動削除。データ品質：文字コードと全角半角を先に決める。文字化けは破損として扱う。

Day1 の 3 つのデモ

① CSV 変換集計

入力 OrderList.csv（受注日、支店、ケース数、入り数、容量、商品名、受注_ID）。支店別に発注数を集計し OrderList_total.csv を出す。変換は Mapper。IF / ループで行単位に加工しない。

② 0 件をエラーにする

ヘッダだけでデータ行がない。出力ファイルを書かず、自らエラー終了。フレームワーク接続後は警告または 255。

③ ファイルトリガー

CSV を入力フォルダへ置く → ①が自動実行 → 結果が出力フォルダへ。トリガーが掛けるのは登録済みサービス。未登録スクリプトではない。

サービス登録：プロジェクト右クリック「プロジェクトをサービスとして登録」。画面で元プロジェクトと対象サービスのスクリプトを比較する。

本番開発はフレームワーク必須 個別スクリプトは処理と End 戻り値だけ。メールは自分で送らない。トリガーは常に SEIYUCOM000X / 01frameworkBatch を呼ぶ。

4 つの出口（Day2 の核心）

戻り値は End コンポーネントのプロパティインスペクタに置く。スクリプト属性に適当な数字を書いてはいけない。

分岐あなたのスクリプトの終わり方フレームワークの動き
1 正常End 戻り値 0成功ログを書いて終了
2 警告戻り値 1–254（デモ：CSV がヘッダのみ / 0 件）警告メール + 警告ログ
3 制御可能な例外戻り値 255、かつ out_* を埋めた異常メール + 異常ログ
4 キャッチ漏れException / catch なしフレームワークが catch して異常メール。戻り値は実際 -1

警告/異常は「警告変数設定」「異常変数設定」で out_component_name/type、out_message_*、out_error_* を埋める。メール後半の例：

FILE0001E|java.io.FileNotFoundException|/data/DSSROOT/DEMO/INPUT/OrderList.csv|CSV読取

読み替え：正常 = 最後まで走った（0）；警告 = 0 件（1–254）；異常 = 読みまたは書き失敗（255 + out_*）。

if_master

DB DSSSEIYU。直す前に手順書 3.1 でバックアップ。リリースでは同じ if_id を DELETE してから INSERT することが多い（P.117）。

正式列名：if_id / if_name / service_name / script_name / from_mail_address / to_mail_address / cc_mail_address / bcc_mail_address / mail_title_header / tier

to_mail_address には必ず isd_support_desk@seiyu.com

DEV：DHUB-DB-DEV:1433。DBeaver 可。アカウントは P.103（パスワードは本頁に書かない）。STG/PROD：RDP + SSMS。SeiyuServerStg.seiyu.com / SeiyuServerPro.seiyu.com。

param_master

IF_ID + param_no + param_value。読んで param1–param20 に置く。

パスやファイル名はできるだけこれらのパラメータにする。アイコン属性に直書きしない。

リリース（リリース手順書 v1.0）

リソース管理者で移行先にログイン 順：プロジェクト → 非プロジェクト資材 → システム表。STG/PROD は SDP。監視は約 1 週間前に ITSM。

5.1 プロジェクト zip

  1. マイプロジェクト → ローカルへダウンロード。「バージョンを指定してダウンロード」を付け、数字が最大の最新版を選ぶ。
  2. 移行先：ローカルからアップロード。上書き = 既存プロジェクトの最新版。別名 = 新しいプロジェクト。
  3. 開く → サービス登録（サービス名 = プロジェクト名）→ マイサービスで確認。
  4. zip は共有を持たない。STG/PROD アップロード後：共有 → SY グループに読み取り。一覧に「共有」と出ること。
  5. スクリプトが Explorer フォルダを書くなら、exec_SY に書き込みグループを付ける（P.110）。

5.2 非プロジェクト（サーバ移行）

  1. コントロールパネル → DataSpiderServerの設定 → サーバ移行。
  2. エクスポートは先に「全て解除」。今回運ぶものだけチェックする。
  3. インポートは外さない「プロジェクトの差分インポート」と「環境変数の差分更新」。外すと全表上書きになる。
  4. インポート後、Windows サービス DataSpiderServista を再起動する。
  5. 同名のとき：サービス/トリガー/グローバルリソースは上書き。環境変数とプロジェクトファイルはスキップできる。ユーザロジックの衝突は name_1 になる。

5.3 システム表

プロジェクトだけでは足りない。if_master を直す前に必ずバックアップする。

DSS 全体を落とす

性能の赤線 IF / ループで行単位加工（Mapper に入れる）。1 スクリプトのアイコンが約 100 を超える。大件数で「大容量データ処理」を付けない（OOM）。PSP と大容量を同時に付けると PSP が優先。PSP は約 1000 件ずつ。塊サイズは変更不可。Designer「表示」で PSP データフローを付けると見える。

やってはいけないこと

  • SEIYUCOM000X / SEIYUCOM001X を改修する
  • スクリプトにパスワード、API Key を直書きする
  • 数珠つなぎ / バラマキ。Designer から本番スクリプトを呼ぶ
  • Databricks グローバルリソースで接続プールを付ける
  • SQL Express をデータベースファイルシステムにする
  • SFTP のパスワード認証（鍵のみ）
  • 本番ログを DEBUG / FINEST にする
  • 研修で失敗したマウント /data/Shared_test を新規スクリプトに書く

PSP はおよそ 1000 件を一塊に並列。テーブル書き込みのバッチは 86 万件で約 30 倍。1 億件級は DSS で担がない。止まったら：My Log → コントロールパネル タスクマネージャでプロセス終了。だめなら DataSpiderServista を再起動。

チェックは本機ブラウザに残る録画と照合するためのもの。アップロードしない。
