## 2. スライド要約

### 1–2 棚割マスタ IF（StoreManagerGX × sinops）

- GX は棚段・棚列 1 始まり、sinops 基本機能は 0 始まり。同じマスが番号 1 ずれ。
- 資料方針: 棚住所機能を今は使わないので **1〜 のまま連携**。住所機能を使うなら 0〜 変換が必要（sinops 側依頼）。
- 対照: Sinops-14。ダミー棚は slide 13 が別途「入っているかどうか」。

### 3–6 センター（DC）発注勧告 — 現状と 3 案

西友現状: sinops-w が勧告数を算出 → IF → TC（基幹）→ DC 発注。

TRIAL 現状: センター自動入れが勧告を抽出するルートは約 1 割。約 9 割は Excel ツールが勧告数を算出し、人が DB 発注ツールで本部発注。

今後 3 案はいずれも **sinops-w の勧告数を起点**:

| 案 | 内容 | 資料上の状態 |
|---|---|---|
| 1 | 人が DB 発注ツールで本発 | 案として提示 |
| 2 | RPA が DB 発注ツールを操作 | 案として提示 |
| 3 | システム連携で発注取り込み | 具体案確認中。TR 基幹 / Himalayas のデータ連携が必要、CoreSaver に流せるか確認中 |

対照: Sinops-22/23 と G-05 倉庫系レイアウト。R の発注 IF 経路を W にそのまま当てない。案 1/2 なら自動発注 GCS を通らない可能性、案 3 なら着地が CoreSaver / Himalayas 側になる可能性。未決。

### 7–8 便振り分け

確認（中島さん経由、畜産）: 対外では便を使わず PC で利用。

- 生鮮: sinops では便振り分けを使わない。振り分けは生鮮発注統合システム。
- 非生鮮: 発注時に便を選ばない。便は物流側？確認中。Hitluster ではなく Himalayas。納品時間の調整に使用。
- 資料結論: **sinops 上で便の設定は持たない**。

対照: G-03 / G-06 の便区分。入荷予定・入荷実績・発注勧告 W のキーとして残っている前提と衝突し得る。昇格しない。

### 9–10 新旧 JAN 紐付け

西友は TC で紐付け → sinops が旧 JAN 実績・在庫を新 JAN 予測に使う。TRIAL 基幹に紐付けなし。

| 案 | 内容 | 懸念 |
|---|---|---|
| 1 | 紐付けせず sinops 新商品 PI | 旧在庫残中の予測精度 |
| 2 | sinops 画面で手動 | 対象が多く作業量 |
| 3 | 取引先が R-melos / eb-mdm で登録、採用分だけ sinops へ | フロー複雑、イレギュラー事故 |
| 4 | 専用メンテ画面。他システムも使うなら sinops 外メンテして同期 | — |

対照: G-02 新旧/クロスリファレンス/代替。未採択。

### 11 ベンダー休み

- sinops-w: メンテナンス画面あり、画面で設定。
- sinops-r: 画面なし、TRIAL 自動発注システムで設定。

対照: Sinops-18。現行アーキテクチャ「18 の源は TRIAL 自動発注連携」は R 側と整合。W 側は画面メンテの可能性。要確認のまま。

### 12–17 勧告数の連携ルート（店舗 / 生鮮 / DC）

非生鮮店舗: sinops →（24/25）→ 自動発注 → EOB（発注 SV）→ CoreSaver。PACER 店舗端末で上下修正可。着地候補メモ: PACERDBSV / OrderSV / 新規 SV。

生鮮: sinops → 自動発注 → 生鮮統合発注 → PACER 生鮮発注 / @rms（青果）/ 市場 EOS・せんどねっと（鮮魚、武田）。精肉はベンダー PC。統合発注→MD→ベンダーは MD 発注実績、→CK は生鮮基幹の発注実績。

DC 在庫版: Excel ツール → DB 発注ツール → CoreSaver。ファイル出力先は DWH / INUNAKI / 集計 SV（Himalayas）/ Databricks に「？」。「新規 IF」とあるが未確定。

slide 15: 翌日以降推奨と週間発注の競合。SY で自動補充するカテゴリは週間発注しないので競合しない。TR 生鮮は販売計画で週 1 回。SY は精肉・青果をやらない。

slide 17（非表示）: tanactl 経由は課題があり全て使わないことを検討中。

対照: 店舗系 R の 2026-09-18 決定（発注 IF → 自動発注 GCS → 既存転送 → OrdreSV）と大枠は同じ話をしている。生鮮と DC は別ルート。本 PPT の OrderSV メモは旧第三候補と同じ層の走り書きであり、R のファイル契約を覆さない。

### 18 tanactl

RAI の発注コントロール。TRIAL 自動発注切替・コンサイメント切替。NTT 調整が必要。通すと発注者 CD が R-CIX になる。棚名称管理で畜産以外は使えない。方針案: **全部使わない**。生鮮側と協議が必要。403 に入れない。

### 19–26 自動発注対象の 4 層（sinops-R6 既存仕様の整理）

出典はプロジェクト格納の IF レイアウト / IF 変換 / IF 一覧（2026-09）。西友 PMI の入口条件として確定した文書ではない。

| 層 | どこ | 内容 |
|---|---|---|
| ① | MD 基幹 | 自動補充対象フラグ OFF は商品マスタ IF に出さない。sinops 内部フラグではない |
| ② | IF 中継 | 扱い無=0 / 削除=1 / 法人別業態別商品マスタ不在は除外。棚割はさらに終了日が過去も除外 |
| ③ | sinops | 商品マスタ開始終了 × 店舗商品 発注開始〜停止。本 PJ 実装では R 向け商品マスタの開始終了は空固定。実質は店別期間 |
| ④ | R6 固有 | 有効な現在棚に載っていること（IF410_01 必須日次）。開始日は勧告計算日。事前有効/無効日数で期間調整。サブ勧告は未来 21 日 |

R と W の非対称: W に棚割 IF なし。W は変換側で発注停止日超過を落とす。R は停止日超過も連携されマスタ残留の注意あり。**R6 と W を同一挙動と仮定しない。**
