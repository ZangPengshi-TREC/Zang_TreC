## 1. スライド要約

### 1.1 アーキテクチャ（スライド1）

標題: **集計GCS → 東京で処理 → 東京GCS**  
副題: 日次バッチ処理申請アーキテクチャ｜**大阪 `asia-northeast2` → 東京 `asia-northeast1`**

| 区分 | 内容 |
|---|---|
| 既存／外部 | **集計SVの GCS**（大阪 `asia-northeast2`）。入力データ TBL / MAT / DM / TANA。毎日更新。`_READY` + manifest |
| 今回申請 | GCP 東京（`asia-northeast1`）＝ `md-data-integration-prod` 実行リージョン |
| 転送 | Storage Transfer（prefix / manifest 指定・差分コピー）。リージョン間は同期時のみ |
| landing | **`md-data-integration-prod` 附帯 GCS**。集計データの保存。日付 `YYYYMMDD` |
| 計算 | Cloud Run Job（**4 vCPU / 16 GiB**）。`md-data-integration-prod` |
| output | **西友連携 GCS**。日付 `YYYYMMDD`。`_SUCCESS`。会社間正本 |
| 制御（案） | Cloud Scheduler → Workflows（READY確認 → 同期完了待ち → Job起動）。**起動主体は TBD（②）** |
| 原則 | 大阪→東京の転送は同期時のみ。landing 読込・計算・output 書込はすべて東京で実行 |

### 1.2 日次シーケンス（スライド2）

一方向実行。失敗時は該当ステップを再試行し、全体を重複起動しない。

| # | ステップ | 内容 |
|---|---|---|
| 01 | 起動 | Scheduler 指定時刻（②未決：Hinemos 経由の可能性あり） |
| 02 | 入力確認 | 大阪の `_READY` を確認 |
| 03 | 同期 | STS 差分コピー → **本PJ附帯 GCS（landing）** |
| 04 | 同期確認 | SUCCESS 待ち・タイムアウト通知 |
| 05 | 計算 | Cloud Run Job（分割／ストリーミング） |
| 06 | 成果物 | **西友連携 GCS output** + `_SUCCESS` |

再試行・冪等:

- 入力／同期失敗 → STS 再試行。日付ディレクトリと変更オブジェクト単位。大阪原本は削除しない
- 計算失敗 → Cloud Run Job 再試行。一時出力ディレクトリ。`_SUCCESS` がある場合のみ完了
- タイムアウト／リソース不足 → オーケストレータが通知。メモリピーク・実行時間・OOMKilled を監視

保持: landing＝入力スナップショット／バックアップ、output＝処理結果。日付単位。Object Versioning または Lifecycle で自動削除。
