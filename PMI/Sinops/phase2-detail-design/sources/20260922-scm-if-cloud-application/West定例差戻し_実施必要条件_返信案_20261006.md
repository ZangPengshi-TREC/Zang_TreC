# West 定例差戻しへの対応（実施必要条件）

日付: 2026-10-06  
相手: MD基幹統合PJ／PJ West 情報システム定例の差戻し  
対象: 提案した SCM連携の GCP 環境構築  
正本費用・構成は変えない。今回足すのは **「なぜ今この機が要るか」** と **「テスト環境と同時に進める」**。

## 差戻しの読み方

原文の承認条件は次の2点。

1. **実施必要な条件を提示すること**
2. **テスト環境等の整理と併せて進行する**

特に①は「明確な理由を説明できなかった」と書かれている。

前回出した GCP 申請 PPT は、**構成・Cloud Run・費用・GKE 比較**まで揃っている。West が足りないと言っているのはそこではない。

足りないのは次の言い切りである。

- どの業務条件が揃っているから、**この GCP 機を実施しなければならないか**
- その条件が揃っていない場合は、**申請しない／後回しにする**
- **dev／stg を本番と切り離して先に整理し、同じ進行で進める**（本番 GCP だけ先に承認しない）

「実施必要な条件」は前提チェックリストではない。  
**この条件が成立しているから実施する**、という業務条件である。

## ① 実施が必要になる条件（これがないと本機は要らない）

次の **7 条件がすべて成立している**ときだけ、SCM連携クラウド機（TRIAL GCP・`md-data-integration` 系・Cloud Run Jobs）の構築が必要になる。1 つでも未合意なら、環境申請は保留する。

| # | 条件（成立していること） | 成立していないとどうなる | 既存資料での位置 |
|---|---|---|---|
| A | Phase2 で、大阪の集計データを **日次** で西友へ渡す IF が必要である | 日次納品が無ければ本機は不要 | PPT 1 |
| B | **型変換・共通化は TRIAL 側 Layer①** で行う。西友 DSS は全フィールド通過であり、変換基盤ではない | 変換を西友 DSS に寄せるなら、TRIAL の変換機は不要 | PPT 1 |
| C | 正本の連携経路は **seiyu-trial-data-exchange**。納品は **最終 TXT のみ・一方向** | 別経路・別形式なら、本申請の GCS／権限設計が崩れる | PPT 1・3・5 |
| D | **元データは連携バケットに入れない**。大阪からコピーした元データは本PJ GCS（landing）に置く | 元データを exchange に置くなら、本PJ GCS 申請の理由が消える | PPT 3・4 |
| E | SCM の連携面は **1 台に集約**する。課題ごとに GCP プロジェクトを割らない | 課題別に既存 PJ へ載せるなら、新規 1 PJ は不要 | PPT 1 |
| F | Layer②③ は **西友 Azure の既存 DataSpider** を使う。本申請で DataSpider／GKE は作らない | 西友側に新規基盤が要るなら、本件の範囲が違う | PPT 1 |
| G | 処理は **必要なときだけ動く日次ファイルバッチ**である（常駐 API ではない） | 常駐サービスなら Cloud Run Jobs 採用理由が立たない | PPT 2 |

**一句话（定例でそのまま読む）**

> 大阪の集計を日次で西友へ渡し、変換は TRIAL の Layer①、正本は seiyu-trial-data-exchange へ最終 TXT のみ、元データは連携バケットに入れない——この 4 点が Phase2 の前提です。その前提が変わらない限り、TRIAL 側に変換付きの統一 IF 機が必要です。既存の西友 DataSpider では変換を代替できません。課題ごとにプロジェクトを割ると連携面が割れるため、新規 1 プロジェクトで実施します。

**やらない場合（West が「本当に要るか」と聞いたとき）**

- Layer① を作らない → 西友へ渡す TXT の型が揃わず、DSS 通過だけでは Phase2 の IF が成立しない。
- 既存の別 GCP プロジェクトへ相乗りする → 元データの隔離と、課題横断の SCM 連携面を同時に守れない。
- 本番だけ先に作る → ②に反する。テスト経路が無い状態で本番 GCS／Job を置くことになる。

## ② テスト環境等の整理と併せて進行する

本申請はもともと **dev／stg／prod の 3 環境**である。差戻しへの答えは「3 環境を費用表に載せた」ではなく、**西友側・連携 GCS・大阪ソースのテスト経路を同じ進行で決めてから構築する**こと。

### 環境の対応（整理してから構築着手）

| 役割 | TRIAL 本申請 | 連携 GCS（松尾さん・別途申請） | 西友 Layer②③ |
|---|---|---|---|
| 開発 | `md-data-integration-dev` | exchange の dev 相当（例: `ods-seiyu-dev`） | 既存 DataSpider の開発／検証経路 |
| 検証 | `md-data-integration-stg` | exchange の stg 相当 | 同上 stg |
| 本番 | `md-data-integration-prod` | exchange の prod | 本番 DSS |

保管期間の前提は現行正本のまま：prod 30 日、stg／dev 7 日。

### 併せて決めること（GCP 承認と同時、または承認条件に書く）

1. **連携バケットの環境分割**（dev／stg／prod のパスと権限）。本体は松尾さん申請。本機の Job は objectCreator のみ。
2. **西友 DSS の受け側**が、どの環境の TXT をテストに使うか。本機から本番バケットへ先に出さない。
3. **大阪集計 GCS** のテスト用 prefix／日付。本番相当量を最初から dev に流さない。
4. **構築順**: 環境対応表が埋まるまで本番 Job の定期起動はしない。先に dev → stg で 6 ステップ（起動〜`_SUCCESS`）を通す。
5. **制御**は申請図どおり Scheduler → Workflows。Hinemos は将来突合であり、テスト環境整理の前提にはしない。

### 進行の約束（定例用）

> GCP 環境の承認は、上記の環境対応を同じ資料に載せたうえでお願いします。構築は dev／stg の経路確認と同時に進め、prod の定期実行はテスト環境の整理が終わってからにします。本番 GCP だけを先行承認する申請ではありません。
