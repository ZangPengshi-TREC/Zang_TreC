### 【スライド 1】背景・なぜ新しいクラウド機を申請するか　／　翻到第 1 页

#### 中文

各位好。今天说明 **SCM連携クラウド機** 的 GCP 环境申请。一共七页：先讲背景，再讲为什么用 Cloud Run，然后是构成、每天怎么跑、规格、费用，最后和 GKE 对比。

先看背景。现在推进的是西友与 TRIAL 的 **MD 基幹統合、PMI 课题的 Phase2 阶段**。每天要把大阪集计侧的数据交到西友侧；TRIAL 与西友之间的正本连携路径是 **seiyu-trial-data-exchange**。型转换和共通化，方针上放在 TRIAL 侧吸收。如果按课题拆多个项目，SCM 统一连携面会裂开，所以要收敛成一台机。

因此需要：在 TRIAL GCP 上申请 **一台 SCM 连携机**；负责见积里的 **Layer①**——取得、转换、配置的批处理；**付帯GCS（元データ）** 和 Cloud Run（处理）一体申请；只把最终 TXT **一方向**交到 **seiyu-trial-data-exchange**。位置上，和现有的惣菜、MD-Link、Inunaki 并列。

为什么说是「新机」。Layer① 是这次要申请的 TRIAL 云机；Layer②③ 是西友 Azure 的 DataSpider，**用既存即可**。DSS 只做全字段通过，转换在 Layer①。本机不挂持久盘，永续只在 GCS。这也是 **PMI 课题 Phase2** 的执行基盤前提。

申请什么、不申请什么。申请：一个项目、Cloud Run Jobs、**本PJ GCS**、Scheduler、Workflows、**STS**（Storage Transfer Service）等。不申请：GKE、本机持久磁盘、DataSpider、以及 **seiyu-trial-data-exchange 本体**——该 GCS 要向松尾另行申请。

一句话：**为了跑通 TRIAL 与西友之间的数据连携，TRIAL 侧需要带转换的统一 IF 基盤，所以申请新建一台 SCM連携クラウド機。**

接下来讲，这台机用什么执行基盤。

#### 日本語

みなさま、本日（ほんじつ）は **SCM連携クラウド機** の GCP 環境（かんきょう）申請（しんせい）をご説明（せつめい）します。全（ぜん）7 枚（まい）です。背景（はいけい）、Cloud Run 採用（さいよう）理由（りゆう）、構成（こうせい）、日次（にちじ）の動（うご）き、スペック、費用（ひよう）、最後（さいご）に GKE 比較（ひかく）の順（じゅん）です。

まず背景です。いま進（すす）めているのは、西友（せいゆう）と TRIAL の **MD 基幹（きかん）統合（とうごう）・PMI 課題（かだい）の Phase2** です。大阪（おおさか）の集計（しゅうけい）系データを日次で西友側へ渡す必要があり、TRIAL と西友の間（あいだ）の正本（せいほん）連携経路（れんけいけいろ）は **seiyu-trial-data-exchange** です。型変換（かたへんかん）と共通化（きょうつうか）は TRIAL 側で吸収（きゅうしゅう）する方針（ほうしん）です。課題（かだい）ごとにプロジェクトを割（わ）ると SCM の統一連携面が割れるため、1 台（だい）にまとめる必要があります。

そのため必要なのは、TRIAL GCP 上の **SCM 連携機を 1 台**。見積（みつもり）の **Layer①**、つまり取得（しゅとく）・変換・配置（はいち）のバッチです。**付帯（ふたい）GCS（元データ）** と Cloud Run（処理）を一体で申請し、最終（さいしゅう）TXT のみ **seiyu-trial-data-exchange** へ一方向（いちほうこう）納品（のうひん）します。位置づけは、既存（きそん）の惣菜（そうざい）・MD-Link・Inunaki と並列（へいれつ）です。

なぜ「新しい機」か。Layer① が今回申請の TRIAL クラウド機、Layer②③ は西友 Azure の DataSpider で **既存を使用**します。DSS は全フィールドを通過、変換は Layer①。本機（ほんき）に永続（えいぞく）ディスクは持たず、永続は GCS のみ。**PMI 課題 Phase2** の実行基盤前提でもあります。

申請する／しない。申請するのは 1 プロジェクト、Cloud Run Jobs、**本PJ GCS**、Scheduler、Workflows、**STS**（Storage Transfer Service／ストレージ転送サービス）など。申請しないのは GKE、本機永続ディスク、DataSpider、**seiyu-trial-data-exchange 本体**です。seiyu-trial-data-exchange は松尾さんへ別途申請します。

一言で言うと、**TRIAL と西友の間のデータ連携を回すため、TRIAL 側に変換付きの統一 IF 基盤が要る。だから新規 1 プロジェクトの SCM連携クラウド機を申請する**、です。

次に、この機をどの実行基盤で作るかを説明します。

### 【スライド 2】なぜ Cloud Run Jobs を採用するか　／　翻到第 2 页

#### 中文

第二页是技术判断。本件不是常驻 API，而是 **需要时才跑的日次文件 IF 批处理**。所以用 **Cloud Run Jobs**，**不上 GKE**。

四个観点。一，動き方：启动→处理→结束，空闲可停；GKE 容易常设集群，批处理易留固定费。二，工作内容：抽出、转换、GCS 推拉；GKE 更适合微服务和常驻 API。三，存储：ステートレス、正本只在 GCS；GKE 往往带节点和卷运维。四，运维费用：Cloud Run 轻；GKE 有集群费，后面用数字对照。

收束：**不是常开的底座，而是需要时才跑的批处理，所以用 Cloud Run Jobs。**

接下来看构成图。

#### 日本語

2 枚目は技術（ぎじゅつ）判断（はんだん）です。本件は常駐（じょうちゅう）API ではなく、**必要なときだけ動く日次ファイル IF バッチ**です。そのため **Cloud Run Jobs** を採用し、**GKE は申請しません**。

観点は四つ。第一、動き方：起動→処理→終了、遊休時は止められる。GKE はクラスタ常設しやすく固定費が残りやすい。第二、仕事：抽出・変換・GCS プッシュ／プル。GKE はマイクロサービス向き。第三、ストレージ：**ステートレス**、正本は GCS のみ。GKE はノード／ボリューム運用が前提になりやすい。第四、運用・費用：Cloud Run は軽い。GKE はクラスタ費があり、数字は後で対比します。

**常時動かす基盤ではなく、必要なときだけ動くバッチなので Cloud Run Jobs**、です。

### 【スライド 3】申請構成図　／　翻到第 3 页

#### 中文

第三页是构成。申请东京 `asia-northeast1` **本PJ GCP**，dev／stg／prod。暂定 ID **md-data-integration-prod**。Layer①＝付帯GCS（元データ）＋ Cloud Run 一体。

左：大阪集计 GCS（既存、不申请）日次数据＋`_READY`。中：STS 复制到本PJ `source-landing/`（约七天／元データ保管），Cloud Run **4 vCPU／16 GiB** 做 SMART，只把最终 TXT upload。右：**seiyu-trial-data-exchange** 的 `result/`＋`_SUCCESS`。

控制：申请图上是 Scheduler → Workflows（READY→STS→Job→验证）——也就是到点启动，按「就绪→拷贝→处理→校验」顺序跑；**将来也有可能改成 Hinemos 启动**（执行体仍是 Cloud Run）。安全边界：源数据只留在本PJ GCS，**不进 seiyu-trial-data-exchange**；西友侧权限压到最小，只能写入（objectCreator）。上传分两路：**大文件用 resumable upload**（可断点续传）；**普通文件处理完直接上传 seiyu-trial-data-exchange**。必要时 ephemeral disk 做外部ソート。无 GKE、无本机持久落地。

#### 日本語

3 枚目は構成図です。東京 `asia-northeast1` の **本PJ GCP**、**dev / stg / prod**。暫定 ID は **md-data-integration-prod**。Layer①＝**付帯GCS（元データ）**＋ Cloud Run の一体です。

左は大阪集計 GCS（既存・今回申請しない）、日次データ＋`_READY`。中央で STS が本PJ `source-landing/`（約 7 日・元データ保管）へコピーし、Cloud Run **4 vCPU / 16 GiB** が SMART 処理、最終 TXT のみ upload。右は **seiyu-trial-data-exchange** の `result/` と `_SUCCESS`。

制御は申請図上 Scheduler → Workflows（READY→STS→Job→検証）——時刻起動し、「READY→コピー→処理→検証」の順で回します。**将来は Hinemos 起動に変わる可能性もあります**（実行体は Cloud Run のまま）。安全境界：元データは本PJ GCS にだけ置き、**seiyu-trial-data-exchange には入れない**。西友側の権限は最小で、書き込みのみ（objectCreator）。アップロードは二通り：**大容量は resumable upload**（途中から再開できる）、**通常ファイルは処理後に seiyu-trial-data-exchange へ直接アップロード**。必要時のみ ephemeral disk を外部ソート領域として使用。GKE と本機永続ステージングは持ちません。

### 【スライド 4】日次実行フロー・権限・処理方針　／　翻到第 4 页

#### 中文

第四页：每天六步——Scheduler → READY／manifest → STS → Cloud Run → 纳品 TXT → `_SUCCESS`（申请图控制流；**将来也可能改成 Hinemos 启动**，执行体仍是 Cloud Run）。SMART 链：解压、选列行、**外部ソート** JOIN、汇总、计算格式、uploader（直送／resumable）。

上传方针：**大文件用 resumable upload**（不整进 RAM）；**普通文件经 Cloud Run 处理后直接上传 seiyu-trial-data-exchange**。权限 STS 大阪读／本PJ 写，Job 本PJ 读／**seiyu-trial-data-exchange** 仅 objectCreator；容量约 251.6 GiB（七天）、転送约每月 1,078 GiB；费用初算约 **一万八千一百九十日元**（第六页明细）。

#### 日本語

4 枚目は日次 6 ステップです。Scheduler → READY／manifest → STS → Cloud Run → TXT 納品 → `_SUCCESS`（申請図上の制御。**将来は Hinemos 起動に変わる可能性あり**。実行体は Cloud Run のまま）。SMART は解凍・selcol／selrow・**外部ソート** JOIN・集計・format・uploader（直送／resumable）。

アップロード方針：**大容量は resumable upload**（RAM に全量を載せない）、**通常ファイルは Cloud Run 処理後に seiyu-trial-data-exchange へ直接アップロード**。権限は STS＝大阪 read／本PJ write、Job＝本PJ objectViewer／**seiyu-trial-data-exchange** objectCreator のみ。容量は元データ約 251.6 GiB（7 日）、転送月約 1,078 GiB。費用初算は約 **1万8,190 円**（明細は 6 枚目）。
