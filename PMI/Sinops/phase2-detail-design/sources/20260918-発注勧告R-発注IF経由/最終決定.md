## 1. 決まったこと

店舗系発注勧告の**ファイル契約**は、CoreSaver 数理発注データ比較でも OrderSV 店別テーブルでもなく、**発注IF `SIREJAN_RCMDORDER_LAST`** である。

層の分担（発注勧告 R）:

| 層 | 担当 | 経路 |
|---|---|---|
| Layer③ | 西友 Azure DataSpider | Sinops → DSS **全フィールド転送** → **連携用 GCS**（型変換・項目選別なし）。GCS 物理名は `kankoku_YYYYMMDDhhmmss.txt` / `subkankoku_YYYYMMDDhhmmss.txt` |
| Layer① | IFクラウド機（SCM連携クラウド機） | 連携用 GCS → **型変換・選別・編集** → **TRIAL 自動発注 GCS** へプッシュ（出力も `_YYYYMMDDhhmmss` 付き） |

Sinops は連携用 GCS へ直送しない。DSS も TRIAL 自動発注 GCS / OrdreSV へは送らない。自動発注 GCS 以降の既存転送 → OrdreSV は 403 の③ではない。

IFクラウド機が作るファイルは、この 7 項目レイアウトに合わせる。

確定ルール:

| ID | 内容 |
|---|---|
| R01 | 参照先を CoreSaver 比較から `SIREJAN_RCMDORDER_LAST` へ変更 |
| R04 / G04 | 推奨発注数量 = 店舗系 No.11 発注バラ数を直接設定。**×1000 しない。** `SIREJAN_RCMDORDER_LAST` の数量は、**発注単位の整数倍であれば可**（倍数への丸め・切捨てはしない） |
| R06 | 納品日 = yyyymmdd 固定長 8。sinops No.4 をそのまま |
| R07 / G05 | Ordertype：0=非日配、1=日配または生鮮。sinops 項目なし。Layer① で付与 |

訂正文（マッピング表）: CoreSaver 数理発注データとの比較を廃止。

### Ordertype（R07）

sinops に Ordertype 項目はない。Layer①（クラウド機）が付与する。Layer③ では作らない。  
**部門CD は TRIAL 商品マスタを見ない。** 発注勧告ファイル（kankoku / subkankoku）に西友分類が載っている。

| 勧告ファイル上の西友分類 | Sinops 階層 |
|---|---|
| 大分類（デパ） | 2、ディビジョン |
| 中分類（西友ライン） | **4、部門** ← `JIHA.BUMON_ZONE` の部門CD |
| 小分類（ファインライン） | 5、カテゴリ |
| 単品JAN | JAN |

1. 採用した勧告ファイルの **中分類（西友ライン）＝部門** を部門CDとする  
2. TRIAL 自動発注 GCS の `JIHA.BUMON_ZONE`（部門CD, ZONECD）で ZONE を引く  
3. 同 GCS の `JIHA.ZONE_LOGIC`（ZONECD, 論理区分）を結合  

| 論理区分 | 意味 | Ordertype |
|---|---|---|
| 01 | 非日配 | `0` |
| 02 | 日配 | `1` |
| 03 | 生鮮 | `1`（日配と同じ） |

引き抜けない部門、または 01/02/03 以外は黙って 0 埋めしない。
