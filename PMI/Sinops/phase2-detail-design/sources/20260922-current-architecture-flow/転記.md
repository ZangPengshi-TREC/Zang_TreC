## 1. スライド1 — 申請対象の構成図

副題: 日次データを大阪から自有東京 GCS へバックアップし、SMART で処理後、**Seiyu GCS へ最終 TXT のみ交付**

### 1.1 区分

| 区分 | 内容 |
|---|---|
| 既存・外部（今回申請しない） | **大阪 集計 GCS**（asia-northeast2）。日次データ + `_READY` |
| 今回申請・常時稼働 | GCP 東京（asia-northeast1）＝ 自有環境 |
| 既存・相手先（容量利用） | **Seiyu 専用 GCS**（東京 asia-northeast1） |

### 1.2 流れ（予測フロー）

1. **Storage Transfer Service**（manifest / prefix）: 大阪 → 自有 Cloud Storage
2. **自有 Cloud Storage**: `source-landing/YYYYMMDD/`、**源データ 7日保管**
3. **Cloud Run Job**: SMART 日次処理、**4 vCPU / 16 GiB**、resumable upload
4. **Seiyu 専用 GCS**: `result/YYYYMMDD/final.txt` + `_SUCCESS`（**最終 TXT のみ**）

読み取り: 原本保管は自有側。SMART は自有 GCS を読取。Seiyu 側は納品先。

### 1.3 制御フロー

- **Cloud Scheduler**: 毎日 指定時刻
- **Workflows**: READY → STS → Job → 検証

### 1.4 安全境界（PPT 明示）

- **源データは Seiyu GCS に入らない。**
- Seiyu 側は **objectCreator のみ**。
- 大容量 TXT: メモリに全量保持せず、**ストリーム + resumable upload**。必要時だけ ephemeral disk を外排に使用。

フッター: **GCP 環境申請 / 源データ隔離・単方向納品**

## 2. スライド2 — 処理・権限・費用前提

### 2.1 日次実行フロー（左 → 右）

| # | ステップ | 内容 |
|---|---|---|
| 01 | Scheduler | 指定時刻に起動 |
| 02 | READY / manifest | 対象ファイル確定 |
| 03 | STS | 自有 GCS へコピー |
| 04 | Cloud Run Job | SMART 店/JAN 処理 |
| 05 | 納品 | 最終 TXT を upload |
| 06 | _SUCCESS | 検証後に作成 |

### 2.2 SMART skills による処理チェーン（例）

解凍 / 索引 → selcol / selrow → 外排 / JOIN → groupby / sumup → scalc / format → stream uploader

### 2.3 大ファイル方針

- Cloud Run の RAM に全量を載せない
- `split_and_sort` / `exchsort` で外排
- **4 vCPU / 16 GiB** は流式処理の初期値

### 2.4 権限方針

| 主体 | 権限 |
|---|---|
| STS | 大阪 **read** → 自有 **write** |
| Job | 自有 **objectViewer** → Seiyu **objectCreator** |
| Scheduler | Workflows **invoker** のみ |

### 2.5 容量・費用の入力値（PPT 記載）

| 項目 | 値 |
|---|---|
| 自有 GCS 源データ | 約 **251.6 GiB**（7日） |
| 大阪→東京転送 | 約 **1,078.4 GiB/月** |
| 結果の重複保存 | **結果を自有 GCS に重複保存しない** |

### 2.6 申請する主なサービス

Cloud Run Jobs / Cloud Storage / STS / Workflows / Cloud Scheduler / Artifact Registry / Logging / Monitoring

### 2.7 本構成の結論（PPT）

- 新規 **GKE は作らず**、**Cloud Run Job** を採用
- **source は自有 GCS**、**result は Seiyu GCS へ単方向交付**
