## 6. 各 IF の詳細設計書構成

各 IF は Phase 1 の ①項目マッピング、②GAP 分析、③変換ルールを入力として、次の構成に展開する。

1. 目的、対象業務、対象データ範囲
2. システム間フローと責任分界（**Data Flow**: 図の箱ごとに Server名／IPまたは接続先／テーブル名／ファイル名。未確定は TBD-DF-xx）
3. 入出力ファイル仕様（ファイル名、方向、文字コード、区切り、改行、ヘッダ、件数）
4. 項目仕様（No、項目名、型/桁、必須、キー、NULL/固定値、編集可否）
5. 変換仕様（入力元、JOIN 条件、抽出条件、編集式、コード変換、丸め）
6. レコード単位、重複排除、洗い替え/差分、削除・無効化
7. ジョブ仕様（起動契機、順序、締め時刻、依存、完了判定）
8. エラー、再送、リカバリ、監視、ログ
9. 性能・件数・同時実行の前提
10. 単体テスト仕様と Phase 1 の GAP / 残課題トレーサビリティ

「①項目マッピング表」はファイルの形、「③変換ルール定義書」は変換の形を示す。詳細設計では、抽出条件・JOIN・異常系・再送条件・テストデータを追加し、二つの資料を実装可能な一つの仕様へ統合する。

## 7. 最初に固定する設計ルール

### 7.0 Layer 分担（2026-09-21 CONFIRMED）

- **DataSpider（Layer②／③）:** 原則として **型変換もフィールド選別もしない。全フィールド処理（通過／Intake／転送）。**
- **Layer①（SCM連携クラウド機）:** **型変換・フィールド選別・コード変換・編集** はすべてここで行う。項目マッピングも **`05_項目マッピング_L①`** に書く。
- **項目マッピング分冊:** `05_…_L①`／`L②`／`L③`。DSS 側（L②・L③）は全フィールド直通のみ。
- 例外は IF ごとに TBD→承認のみ。詳細は `DD-00-common-interface-design.md` §3.0。

### 7.1 商品/店舗商品マスタ

- `item_mst.txt` は 16 項目、`store_item_mst.txt` は 13 項目を対象とする。
- 商品コードは TRIAL JAN から Sinops の商品コードへ変換する。Phase 1 には右端 13 桁ルールがあるため、先頭 0 の扱いと 13 桁超過/不足を単体テストに入れる。
- メーカーコードは現時点の合意どおりブランクを基本値とする。
- item 側の発注単位は、同一商品に複数の店別発注単位が存在する場合、店舗数が最も多い値を採用する。store 側は店別調達マスタの値を使用する。
- 標準原価は Master の `cost`（税抜）を候補とする。標準売価は `price` / `price_intax` のどちらを Sinops へ出すか、税区分・税率の参照元と端数処理を確定するまで固定しない。
- `発注開始日` / `発注終了日` は店別管理を優先し、未設定時の空文字列扱いを Sinops の仕様と合わせてテストする。
- Phase 1 の分類ルールには桁数の旧前提が残る。意味上の対応（西友の大分類→Sinops 2、 中分類→4、 小分類→5）は反映するが、最終のフィールド長・ゼロ埋め・切捨ては最新 Sinops レイアウトと G-01 の決定を優先する。

### 7.2 ケース・バラ

- 対象は `case_bara.txt` の 6 項目。代表 ID と JAN が同一の単品行、削除済み行、ケース→ボールの除外条件を明示する。
- 発注商品フラグは発注勧告に直結するため、`ISSTOPORDER` の参照粒度と、同一バラ商品コードに対する 1 件制約を確定するまで最終値を固定しない。
- 新旧紐付け、クロスリファレンス、代替商品コードは、採用/廃止を決めた後に別ルール ID として実装する。代替機能を廃止する場合は「IF から除外」とテストケースに残す。

### 7.3 発注スケジュール・便区分

- 発注スケジュールは現行 TRIAL の階層別設定をベースに、Sinops の発注日・納品日・締め時刻の生成ルールを分離して記載する。
- 仕入先コードは残課題 No.8 では西友 9 桁を移行する回答だが、Master 統合側の `取引先マスタ.code`、`商品調達マスタ.vendor_id`、`発注締時間マスタ.vendor_id` は最大 8 桁である。桁数、保持先、Sinops 出力値を決めるまで `TBD` とする。
- 商品共通の分類は `商品共通マスタ（商品分類項目追加版）` の `base_org`、`base_div`、`base_line`、`base_upper1`〜`base_upper5` を候補とする。旧版の階層コードをそのまま実装しない。
- `店舗商品マスタ` は税抜売価 `price` と税込売価 `price_intax` の両方を持つ。残課題 No.6 の売価税込・原価税抜の回答と Sinops 出力項目の関係、税率参照、端数処理を確定するまで売価変換を固定しない。
- HHmm の締め時刻は CoreSaver/MT type 等の供給元を確定するまで `TBD`。IF 内に固定値を埋め込まない。
- 便区分は入荷予定/入荷実績/発注勧告 W で共通のキー項目として管理し、固定値・別テーブル・新規連携のいずれかを G-03 で決定する。

### 7.4 在庫・自動補充側の棚割依存・新商品

- 店舗在庫は現時点で Shinise 営業在庫を第一候補とする。センター在庫は現行入力契約を前提とし、Hitluster/Himalaya 本体の設計は対象外とする。
- `Sinops-14` は自動補充側が受け取る棚割入力の契約だけを対象とする。棚割システム、棚割 DB、Store Manager、店 Power の方式設計は対象外であり、未確定事項は外部依存として記録する。
- `Sinops-15` は自動補充側の新商品抽出条件、自動発注対象フラグ、参照する在庫断面を一つの処理仕様として記載する。棚割側のデータ生成・システム変更は対象外とする。

## 8. 完了条件

IF ごとに、以下を満たしたものだけを「詳細設計完了」とする。

- 入力元と出力先が一意に決まっている。
- 全必須項目の値、型、桁、キー、NULL/固定値が定義されている。
- 抽出・JOIN・変換・除外・重複・削除のルールを例付きで再現できる。
- 正常系、0 件、欠損、重複、桁超過、異常終了、再送の単体テストがある。
- 関連残課題の決定 ID、回答日、根拠ファイルが追跡できる。
- 未確定値は `TBD`、設計仮定は `ASSUMPTION` と明示され、製造開始条件が設定されている。

## 9. 最初の作業パッケージ

最初の設計対象は、後続 IF から参照される `DD-00` と、マスタ基盤の 01/02/03/04 とする。実作業では次の順で Phase 1 資料を詳細設計へ変換する。

1. `phase1-pack` の ①/②/③ を IF ごとに同じ版へそろえる。
2. 最新レイアウトと残課題表から、確定値・仮定・未確定を分離する。
3. 対象範囲とコード変換を `DD-00` に集約する。
4. 01/02 を先に設計し、03/04 を同じコード表と共通エラー仕様へ接続する。
5. 01/02 の代表データで単体テスト骨子を作り、ケース・バラとスケジュールへ横展開する。

残課題との対応表は `traceability-matrix.csv` に置く。設計中に判断が変わった場合は、仕様だけを直接修正せず、先に対応表の決定状態と根拠を更新する。
