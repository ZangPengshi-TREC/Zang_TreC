## 本文（約 1 分〜1 分半）

今日は、SCM連携クラウド機の申請範囲をご説明します。

申請対象は、TRIAL GCP の新規 1 プロジェクトです。資料の ProjectD は例で、正式名ではありません。既存の惣菜（そうざい）、MD-Link、Inunaki と並列（へいれつ）する連携機です。

担当は見積（みつもり）の Layer① です。ファイルの出し入れだけでなく、共通化・型変換（かたへんかん）と、一部の生成ロジックも本機で行います。往路（おうろ）は集計 SV から抽出（ちゅうしゅつ）し、変換して本機に保存し、連携用 GCS へ出します。復路（ふくろ）の発注勧告（かんこく）は、Layer③ の DataSpider が Sinops から処理して連携用 GCS へ出します。Layer① のクラウド機がそれをプルし、処理したうえで TRIAL 自動発注の GCS へ上げます。OrdreSV へは既存の自動発注転送が届けます。クラウド機は直結（ちょっけつ）しません。

Layer② と Layer③ は西友 Azure の DataSpider です。② はマスタの Intake、③ は往路の Sinops と BO への転送、および復路の発注勧告を連携用 GCS へ出す処理です。GCS と DataSpider は今回のクラウド機 Spec には入りません。連携用 GCS は松尾さんへ別途申請します。

計画です。今週中に、SCM連携クラウド機の機能範囲を引き続き固めます。来週までに、中国側の担当チームでアーキテクチャを確認し、Spec と費用を算出します。その後、岩瀬さんへお渡しして、ご提案いただきます。

以上です。

## 聞かれたら足す（本文には入れない）

**なぜ IF クラウド機と呼ばないのですか。**  
見積の Layer① では外部 IF と書きますが、本機では共通化・型変換と一部の生成も行います。そのため SCM連携クラウド機と呼んでいます。

**往路は全部集計 SV から取りますか。**  
いいえ。多くは集計 SV です。新商品在庫はクラウド機が西友 DWH 棚割 × TRMD マスタで生成します。仕入先休日の源は TRIAL 自動発注連携です。発注勧告（かんこく）は Layer③ の DataSpider が Sinops から処理して連携用 GCS へ出し、Layer① のクラウド機がプルして処理し、TRIAL 自動発注の GCS へ上げます。

**GCS は Spec に入らないので、申請しなくてよいですか。**  
今回の Spec はクラウド機だけです。連携用 GCS はクラウド機のプロジェクトではありませんが、松尾さんへ別途申請します。DataSpider も今回の Spec には入りません。

**連携用 GCS と自動発注 GCS は別ですか。**  
別です。連携用 GCS が TRIAL 側と西友側をつなぐ唯一の通路です。自動発注 GCS は TRIAL 内の既存機能で、勧告（かんこく）を OrdreSV へ渡す受け皿です。どちらもクラウド機のプロジェクトではありません。

**なぜ 1 プロジェクトなのですか。**  
SCM の統一連携面を割らないためです。課題ごとに別プロジェクトにすると、Hinemos の起動先とファイルの置き場が二系統（にけいとう）になります。

**資料の ProjectD は正式名ですか。**  
いいえ。既存の A 惣菜（そうざい） / B MD-Link / C Inunaki に並べて説明するための仮の呼び方です。正式なプロジェクト ID は未定です。

**BO や共通基盤は。**  
BO プログラムは本段階の対象外ですが、同じクラウド機と DataSpider を使います。共通基盤の立ち上げはハブ側であり、クラウド機上の連携・変換そのものではありません。

**Inunaki の PSC は。**  
ネットワーク前提です。今回申請するクラウド機の機能範囲ではありません。バケット契約との最終対応は未突合（みとつごう）です。
