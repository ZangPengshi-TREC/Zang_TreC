## 申請するもの（口頭の要約）

| 申請する | 申請しない（今回のクラウド機 Spec 外） |
|---|---|
| TRIAL GCP **新規 1 プロジェクト**（SCM連携クラウド機） | **GKE**（常設クラスタは不要） |
| 実行基盤は **Cloud Run Jobs**（無状態のバッチ。Hinemos 起動） | 本機の**永続ディスク／ステージング** |
| （別途）連携用 GCS → 松尾さん | DataSpider（西友 Azure。②③） |
| | 自動発注 GCS（TRIAL 既存。クラウド機 PJ ではない） |

要点: 本機は **ファイル IF のバッチ変換機**。起動→抽出・変換→GCS へプッシュ／プル→終了。常時稼働のマイクロサービス基盤ではないので **Cloud Run Jobs**。GKE は申請しない。

### なぜ Cloud Run で GKE ではないか（対比・口頭用）

| 観点 | **Cloud Run Jobs（採用）** | **GKE（不採用）** |
|---|---|---|
| 動き方 | Hinemos で起動 → 処理 → 終了。遊休時は止まれる | クラスタ・ノードを常設しやすい |
| 本機の仕事 | 抽出・変換・GCS プッシュ／プルの**バッチ** | 向きはマイクロサービス／常時 API |
| ストレージ | 無状態。正本は GCS。設計と一致 | ノード／永続ボリューム運用が前提になりがち |
| 運用・費用 | 申請・運用が軽い。バッチ向きの従量 | 運用負荷・固定費が大きい。今回は過剰 |
| 結論 | **IF 連携機に適合** | **今回のスコープには不要** |

口頭ワンフレーズ: 「常時動かす基盤ではなく、必要なときだけ動くバッチなので Cloud Run Jobs。GKE は常設クラスタ前提で、今回の IF 機には過剰です。」

## 本文（約 2 分〜2 分半）

今日は、SCM連携クラウド機の申請範囲をご説明します。何を申請するか、なぜその実行基盤か、往路と復路で何をするか、どこまでが今回の Spec か、の四点です。

まず申請対象です。TRIAL GCP に **新規 1 プロジェクト** を立てます。資料に出てくる ProjectD や Seiyu_Order は説明用の仮称で、正式なプロジェクト ID ではありません。位置づけは、既存の惣菜（そうざい）、MD-Link、Inunaki と並列（へいれつ）する **SCM の連携機** です。課題ごとにプロジェクトを割ると、Hinemos の起動先とファイルの置き場が二系統になるため、**1 プロジェクトにまとめます。**

次に実行基盤です。採用は **Cloud Run Jobs** です。本機の仕事は、API を常時待ち受けるサービスではなく、**Hinemos から時刻起動されるバッチ** です。流れは、起動 → 集計 SV などから抽出（ちゅうしゅつ）→ 共通化・型変換（かたへんかん）→ 連携用 GCS へプッシュ、あるいは連携用 GCS からプルして変換 → 終了、です。遊休時にノードを抱え続ける必要はありません。対して **GKE** はクラスタとノードを常設する前提が強く、運用負荷と固定費が大きくなります。今回はファイル IF の変換機であり、マイクロサービス基盤ではないので、**GKE は申請しません。** あわせて、本機に **永続のステージング領域は持ちません。** 成果物の正は GCS 側です。ジョブ実行中の一時領域だけは可とします。

担当範囲は見積（みつもり）の **Layer①** です。単なるファイルの出し入れではなく、西友と TRIAL の差分を吸収する **共通化・型変換**、および一部の生成ロジックも本機で行います。  
往路（おうろ）は、主に集計 SV から抽出し、変換したうえで **連携用 GCS へ直接プッシュ** します。西友と TRIAL の会社間の唯一の通路は、この連携用 GCS です。  
復路（ふくろ）の発注勧告（かんこく）は、まず西友 Azure の **Layer③ DataSpider** が Sinops から処理し、連携用 GCS へ出します。そのあと **Layer① のクラウド機** がプルし、発注 IF 形式へ変換して **TRIAL 自動発注 GCS へプッシュ** します。OrdreSV へ届けるのは、既存の自動発注転送です。クラウド機から OrdreSV へは直結（ちょっけつ）しません。自動発注 GCS は TRIAL 内の既存受け皿で、今回のクラウド機プロジェクトには含めません。

Layer② と Layer③ は西友 Azure の DataSpider です。② はマスタの Intake、③ は往路の Sinops・BO への転送、および復路の勧告を連携用 GCS へ出す処理です。**DataSpider と GCS 本体は、今回のクラウド機 Spec には入りません。** ただし連携用 GCS そのものは松尾さんへ **別途申請** が必要です。BO プログラムは本段階の対象外ですが、同じクラウド機と DataSpider の面は使います。

最後に計画です。今週中に、SCM連携クラウド機の機能範囲を引き続き固めます。来週までに、中国側の担当チームでアーキテクチャを確認し、Spec と費用を算出します。その後、岩瀬さんへお渡しして、ご提案いただきます。

以上です。説明の要点は、「1 プロジェクトの連携機」「Cloud Run Jobs のバッチ、GKE は不要」「永続は GCS、本機は無状態」「往路は連携用 GCS へプッシュ、復路はプルして自動発注 GCS へ」「DSS と GCS は別申請・別 Spec」です。

## 聞かれたら足す（本文には入れない）

**なぜ IF クラウド機と呼ばないのですか。**  
見積の Layer① では外部 IF と書きますが、本機では共通化・型変換と一部の生成も行います。そのため SCM連携クラウド機と呼んでいます。

**なぜ Cloud Run で、GKE ではないのですか。**  
対比は上表のとおりです。本機は「起動→変換→GCS→終了」のバッチ。Cloud Run Jobs はそれに合う。GKE は常設クラスタ・ノード運用が前提で、無状態・永続ストレージなしの IF 機には過剰です。将来、常時 API や複雑なサービスメッシュが必要になれば再評価しますが、今回の申請範囲ではありません。

**DataSpider で型変換や項目の絞り込みはしますか。**  
原則しません。DSS（Layer②／③）は **全フィールドを通す** だけです。型変換・フィールド選別・コード変換・編集は **Layer①（本クラウド機）** で行います。

**往路は全部集計 SV から取りますか。**  
いいえ。多くは集計 SV です。新商品在庫はクラウド機が西友 DWH 棚割 × TRMD マスタで生成します。仕入先休日の源は TRIAL 自動発注連携です。発注勧告（かんこく）は Layer③ の DataSpider が Sinops から処理して連携用 GCS へ出し、Layer① のクラウド機がプルして処理し、TRIAL 自動発注の GCS へプッシュします。

**本機にディスクを持ちますか。**  
永続のステージング領域は持ちません。成果物の正は連携用 GCS（復路の発注IFは自動発注 GCS）です。ジョブ実行中の一時領域は可です。

**GCS は Spec に入らないので、申請しなくてよいですか。**  
今回の Spec はクラウド機だけです。連携用 GCS はクラウド機のプロジェクトではありませんが、松尾さんへ別途申請します。DataSpider も今回の Spec には入りません。

**連携用 GCS と自動発注 GCS は別ですか。**  
別です。連携用 GCS が TRIAL 側と西友側をつなぐ唯一の通路です。自動発注 GCS は TRIAL 内の既存機能で、勧告（かんこく）を OrdreSV へ渡す受け皿です。どちらもクラウド機のプロジェクトではありません。

**なぜ 1 プロジェクトなのですか。**  
SCM の統一連携面を割らないためです。課題ごとに別プロジェクトにすると、Hinemos の起動先とファイルの置き場が二系統（にけいとう）になります。

**資料の ProjectD は正式名ですか。**  
いいえ。既存の A 惣菜（そうざい） / B MD-Link / C Inunaki に並べて説明するための仮の呼び方です。正式なプロジェクト ID は未定です。

**BO や共通基盤は。**  
BO プログラムは本段階の対象外ですが、同じクラウド機と DataSpider を使います。共通基盤の立ち上げはハブ側であり、クラウド機上の連携・変換そのものではありません。

**Inunaki の PSC は。**  
ネットワーク前提です。今回申請するクラウド機の機能範囲ではありません。バケット契約との最終対応は未突合（みとつごう）です。
