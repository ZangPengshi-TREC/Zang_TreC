## 本文（約 1 分半〜2 分）

今日は、西友 MD 基幹（きかん）統合で申請する、SCM 統一 IF クラウド機の範囲をご説明します。

申請対象は、TRIAL GCP 上の新規 1 プロジェクトです。資料では仮に ProjectD、Seiyu_Order と呼んでいますが、これは例です。正式なプロジェクト名ではありません。既存の惣菜（そうざい）、MD-Link、Inunaki と並列（へいれつ）する IF 機、という位置づけです。

クラウド機が担当するのは、見積（みつもり）の Layer①、外部 IF だけです。機能は四つです。

第一に、集計 SV からの往路抽出（ちゅうしゅつ）です。基幹（きかん）データは集計 SV に出ます。クラウド機はそこから往路 IF を取り出します。往路のすべてを集計 SV から取るわけではありません。新商品在庫は本機で生成、仕入先休日は自動発注連携、発注勧告（かんこく）は復路（ふくろ）で連携用 GCS から取得します。

第二に、共通化と型変換（かたへんかん）、および本機保存です。西友側と TRIAL 側で桁（けた）やコードが違うところをここで揃（そろ）え、変換後ファイルをステージングします。

第三に、往路（おうろ）のファイル出力です。変換後ファイルを連携用 GCS へ置きます。

第四に、復路（ふくろ）の取得と引き渡しです。西友側が連携用 GCS に置いた発注勧告（かんこく）をクラウド機が取得し、TRIAL 自動発注の IF へ変換して、自動発注側の GCS へ置きます。OrdreSV へは既存の自動発注転送が届けます。クラウド機は OrdreSV へ直結（ちょっけつ）しません。

周辺です。Layer② と Layer③ は西友 Azure の DataSpider です。② は必要なマスタの Intake、③ は Sinops と BO への転送と、勧告（かんこく）の受信です。二次加工はしません。TRIAL 側と西友側をつなぐ通路は連携用 GCS のみです。GCS と DataSpider は今回のクラウド機 Spec には入りません。連携用 GCS は松尾さんへ別途申請します。Hinemos は Layer① をこの新規プロジェクト、Layer②③ を西友 DataSpider で起動します。

以上です。申請したいのは、抽出（ちゅうしゅつ）、変換、保存、ファイル出入力（しゅつにゅうりょく）を行う、TRIAL 側の外部 IF 用 1 プロジェクトです。

## 聞かれたら足す（本文には入れない）

**往路は全部集計 SV から取りますか。**  
いいえ。多くは集計 SV です。新商品在庫はクラウド機が西友 DWH 棚割 × TRMD マスタで生成します。仕入先休日の源は TRIAL 自動発注連携です。発注勧告（かんこく）は連携用 GCS から取得します。

**GCS は Spec に入らないので、申請しなくてよいですか。**  
今回の Spec はクラウド機だけです。連携用 GCS はクラウド機のプロジェクトではありませんが、松尾さんへ別途申請します。DataSpider も今回の Spec には入りません。

**連携用 GCS と自動発注 GCS は別ですか。**  
別です。連携用 GCS が TRIAL 側と西友側をつなぐ唯一の通路です。自動発注 GCS は TRIAL 内の既存機能で、勧告（かんこく）を OrdreSV へ渡す受け皿です。どちらもクラウド機のプロジェクトではありません。

**なぜ 1 プロジェクトなのですか。**  
SCM の統一連携面を割らないためです。課題ごとに別プロジェクトにすると、Hinemos の起動先とファイルの置き場が二系統（にけいとう）になります。

**資料の ProjectD は正式名ですか。**  
いいえ。既存の A 惣菜（そうざい） / B MD-Link / C Inunaki に並べて説明するための仮の呼び方です。正式なプロジェクト ID は未定です。

**BO や共通基盤は。**  
BO プログラムは本段階の対象外ですが、同じクラウド機と DataSpider を使います。共通基盤の立ち上げはハブ側であり、クラウド機の外部 IF 機能そのものではありません。

**Inunaki の PSC は。**  
ネットワーク前提です。今回申請するクラウド機の機能範囲ではありません。バケット契約との最終対応は未突合（みとつごう）です。
